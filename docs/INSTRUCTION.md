# Пошаговая инструкция по выполнению проекта

Этот документ ведёт тебя от первого запуска до готовой сдачи. Иди строго
по шагам — порядок продуман так, чтобы тема была понятна, даже если ты
никогда не занимался веб-безопасностью.

Условные обозначения:
- 🖥️ — команда в терминале;
- 🌐 — действие в браузере;
- ✅ — контрольная точка: как понять, что шаг выполнен.

Параллельно держи открытыми:
- [docs/TASKS.md](TASKS.md) — подсказки по каждой уязвимости (без готового кода);
- [docs/VULNERABILITIES.md](VULNERABILITIES.md) — сюда пишешь отчёт;
- [docs/GRADING.md](GRADING.md) — критерии оценки (уровни Б / П / Э): полезно
  прочитать **до начала**, чтобы понимать, на что претендуешь.

Список инструментов и справочных ссылок (Node.js, Express, OWASP, MDN,
CWE) — в разделе «Инструменты и материалы» в [README](../README.md).

## Что вообще нужно сделать (цель проекта)

В приложении есть 7 заранее внесённых уязвимостей. Твоя работа:
1. **Найти** каждую и **воспроизвести атаку** на локальном стенде.
2. **Починить** её правильным способом.
3. Показать, что **Content-Security-Policy (CSP)** блокирует атаку даже
   при оставленной уязвимости — как второй рубеж защиты.
4. Сдать: исправленное приложение (проходит автотесты), заполненный
   отчёт и видео с демонстрацией «до и после».

## Шаг 0. Подготовка окружения

Нужен **Node.js версии 18 или новее**.

🖥️ Проверь версию:
```bash
node -v
```

🖥️ Установи зависимости (один раз):
```bash
npm install
```

✅ Папка `node_modules` появилась, ошибок нет.

> Если `npm install` падает на сборке `better-sqlite3` — поставь
> инструменты сборки: на macOS `xcode-select --install`, на Linux пакет
> `build-essential`.

## Шаг 2. Посмотри на автотесты (карта работы)

Автотесты — твой главный ориентир. Они проверяют **правильное**
(защищённое) поведение, поэтому сейчас часть из них красная.

🖥️ В новом окне терминала (сервер пусть работает):
```bash
npm test
```

✅ Ты увидишь примерно `# pass 2`, `# fail 6`. Это нормально и ожидаемо:
6 падающих тестов = 6 ещё не закрытых проблем. Каждое сообщение об ошибке
по-русски называет суть (например, «инъекция в логине всё ещё проходит»).

Запомни правило цикла: **после каждого исправления снова запускай
`npm test`** и смотри, как красное становится зелёным.

## Шаг 4. Главный цикл: по одной уязвимости за раз

Для **каждой** уязвимости повторяй один и тот же цикл из 4 действий.
Делай их в порядке VULN#1 → … → VULN#7.

> **Сначала атака, потом починка.** Пока не увидел проблему своими
> глазами — не исправляй. Это и есть обучение.

### 4.1. Воспроизведи атаку
Возьми сценарий из [docs/TASKS.md](TASKS.md) для этой уязвимости и
проделай его в браузере (а для CSRF — через стенд атакующего, см. Шаг 5).

### 4.2. Запиши в отчёт
Открой [docs/VULNERABILITIES.md](VULNERABILITIES.md) и заполни карточку:
что за уязвимость, какой нагрузкой воспроизводится, что получает
атакующий. **Делай это до починки**, пока атака ещё работает.

### 4.3. Почини
Исправь код правильным способом (подсказки — в TASKS.md). Сохрани файл и
перезапусти сервер (`Ctrl+C`, затем `npm start`).

### 4.4. Проверь
🖥️ `npm test` — соответствующий тест должен позеленеть. Повтори атаку из
4.1 — она больше не срабатывает.

### Шпаргалка «уязвимость → как чинится»

| # | Что | Коротко про исправление |
|---|-----|--------------------------|
| 1 | SQL-инъекция в поиске | параметризованный запрос (плейсхолдер `?`) |
| 2 | SQL-инъекция в логине | параметризованный запрос |
| 3 | Небезопасная cookie | флаги `httpOnly`, `sameSite` |
| 4 | CSRF | проверять CSRF-токен на POST-запросах |
| 5 | DOM XSS | `textContent` вместо `innerHTML` |
| 6 | Stored/Reflected XSS | экранировать вывод помощником `esc()` |
| 7 | Нет CSP | заголовок `Content-Security-Policy` |

> **Важный вывод по ходу дела:** для SQL-инъекций и XSS обрати внимание,
> почему проверка ввода *на клиенте* (в браузере) не защищает — запрос
> можно отправить напрямую, минуя страницу (через DevTools или `curl`).
> Защита всегда на сервере и при выводе данных. Зафиксируй эту мысль в
> отчёте.

## Шаг 5. Как пользоваться стендом атакующего (для CSRF и XSS)

«Атакующий сайт» — это отдельный сайт на другом порту, который играет
роль злоумышленника.

🖥️ В **отдельном** терминале (основной сервер тоже должен работать):
```bash
npm run attacker
```

🌐 Убедись, что ты **залогинен** на DevBoard (<http://localhost:3000>),
затем открой <http://localhost:4000>.

Что произойдёт на уязвимой версии:
- страница «атакующего» автоматически отправит сообщение на доску **от
  твоего имени** (это CSRF — VULN#4);
- ссылка «Открыть ваш профиль» несёт XSS-нагрузку в адресе (VULN#5).

После починки VULN#3 + VULN#4 межсайтовый запрос перестанет проходить, а
после VULN#5 — нагрузка в профиле перестанет выполняться. Повтори заход
на стенд и убедись в этом.

✅ Ты своими глазами увидел атаку «до» и её отсутствие «после».

## Шаг 6. Эксперимент с Content-Security-Policy (обязательный пункт)

Цель — показать, что CSP работает как **второй рубеж**: блокирует атаку,
даже если уязвимость осталась.

1. Выбери одну XSS (удобнее всего VULN#6) и **пока не чини её** — либо,
   если уже починил, временно верни как было.
2. Добавь заголовок `Content-Security-Policy` (см. TASKS.md, задание 7):
   `script-src 'self'` **без** `unsafe-inline`.
3. 🌐 Повтори XSS-атаку (отправь сообщение с нагрузкой). Открой в браузере
   DevTools → вкладка Console.
4. ✅ Нагрузка в HTML присутствует, но **не выполняется**, а в консоли
   появляется сообщение о блокировке политикой CSP. Сделай скриншот — он
   пригодится в отчёте и видео.
5. Теперь почини XSS окончательно и **оставь CSP включённой**.

> Побочный эффект: inline-скрипты на странице перестанут работать после
> включения CSP. В этом проекте скрипт профиля уже вынесен в отдельный
> файл `public/profile.js` — это и есть правильный шаблон.

## Если что-то пошло не так (быстрая помощь)

- **`npm start` не стартует, порт занят** — закрой прошлый сервер
  (`Ctrl+C`) или задай другой порт: `PORT=3001 npm start`.
- **Правки в коде не видны** — перезапусти сервер. Либо запускай через
  `npm run dev` (перезапускается сам при изменениях).
- **Хочу начать данные с нуля** — выполни `npm run seed` (пересоздаёт
  учебную базу со стартовыми сообщениями).
- **Стенд атакующего «ничего не делает»** — проверь, что ты залогинен на
  DevBoard и что основной сервер на порту 3000 запущен.
