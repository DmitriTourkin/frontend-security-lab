# Задания

Работайте по уязвимостям сверху вниз. Для каждой: **воспроизведите →
зафиксируйте в отчёте → почините → перезапустите тесты**.

Подсказки намеренно не дают готовый код. Эталон — в `SOLUTION.md`,
загляните туда только после своей попытки.

---

## 0. Разведка

- `npm install`, затем `npm test` — посмотрите на красные тесты.
- `npm start`, откройте доску, залогиньтесь под `alice`.
- Найдите в `src/server.js` все комментарии `VULN#`.

## 1 и 2. SQL-инъекции (`VULN#1`, `VULN#2`)

**Воспроизведение — логин:**
в форму входа введите логин `admin'--` и любой пароль. Либо логин
`' OR '1'='1` и такой же пароль. Вы вошли без знания пароля.

**Воспроизведение — поиск:**
в строке поиска на доске введите
`%' UNION SELECT username, password, role FROM users -- `
— и в ленте появятся логины и пароли всех пользователей.

**Почему проверка ввода на клиенте не спасает:**
клиентскую валидацию (`maxlength`, проверки в JS) легко обойти — запрос
можно отправить напрямую (`curl`, DevTools, Postman), минуя страницу.
Проверка на клиенте — это про удобство, а не про безопасность.

**Исправление:** замените конкатенацию строк в SQL на параметризованные
запросы (`?`-плейсхолдеры `better-sqlite3`). Значение пользователя должно
попадать в движок БД как *данные*, а не как часть текста запроса.

## 3. Атрибуты cookie (`VULN#3`)

**Воспроизведение:** залогиньтесь, откройте DevTools → Console, введите
`document.cookie`. Видно `sid=...` — значит, любой XSS-скрипт может
украсть сессию. Отсутствие `SameSite` — часть причины, почему работает
CSRF (задание 4).

**Исправление:** выдавайте cookie с `httpOnly: true`, `sameSite: 'lax'`
(или `'strict'`) и `secure: true` для HTTPS-продакшена.

## 4. CSRF (`VULN#4`)

**Воспроизведение:** будучи залогиненным на DevBoard, запустите
`npm run attacker` и откройте <http://localhost:4000>. Чужой сайт
автоматически отправит сообщение на доску от вашего имени — вы его не
писали.

**Исправление:** внедрите CSRF-токен. Токен уже кладётся в сессию при
логине (поле `csrf`). Нужно:
- отдавать токен в формы (скрытое поле `_csrf`);
- на `POST /comment` и `POST /delete/:id` сверять присланный токен с
  токеном сессии и отклонять запрос (403) при несовпадении.

Автотест ожидает, что токен принимается в поле формы `_csrf`.

## 5. DOM-based XSS (`VULN#5`)

**Воспроизведение:** откройте
`http://localhost:3000/profile#name=<img src=x onerror=alert(1)>`
— выполнится произвольный JS. Через стенд атакующего это оформлено
ссылкой «Открыть ваш профиль».

**Почему сервер бессилен:** часть URL после `#` браузер на сервер не
отправляет. Серверная валидация тут физически не видит нагрузку —
исправление возможно только на клиенте.

**Исправление:** в `public/profile.js` вставляйте имя через `textContent`
(или безопасное создание узлов), а не через `innerHTML`.

---

## 6. Stored / Reflected XSS (`VULN#6`)

**Воспроизведение:** отправьте сообщение
`<img src=x onerror="alert(document.cookie)">` — оно сработает у каждого,
кто откроет доску (stored XSS). Значение поиска `q` тоже отражается.

**Исправление:** экранируйте любые пользовательские данные при выводе в
HTML. В `src/server.js` уже есть готовый помощник `esc()` — примените его
к `author` и `body` в списке сообщений (и везде, где данные попадают в
разметку).

## 7. Content-Security-Policy (`VULN#7`)

Это **второй рубеж обороны**. Задача — показать, что даже при оставленной
XSS-уязвимости CSP не даёт нагрузке выполниться.

**Шаги:**
1. Временно верните (или не чините) одну XSS — например `VULN#6`.
2. Добавьте middleware с заголовком `Content-Security-Policy`, где
   `script-src 'self'` (без `unsafe-inline`), `object-src 'none'`,
   `base-uri 'self'`.
3. Повторите XSS-атаку: браузер заблокирует и inline-обработчики
   (`onerror=`), и сторонние скрипты. В консоли появится отчёт о
   нарушении CSP.
4. Почините XSS окончательно и оставьте CSP включённой.

**Замечание:** инлайновый `<script>` на странице профиля после включения
CSP перестанет работать — вынесите его в файл (`profile.js` уже вынесен),
это и есть правильный шаблон.
